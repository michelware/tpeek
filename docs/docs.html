Documentation

Everything TPeek does, in the order you meet it. TPeek is one command with five flags: it listens on one address, forwards to one target, and prints what goes through.

1. Install

TPeek ships as 5 standalone binaries. Download the one for your platform from the latest release:

PlatformFile
Linux x64tpeek-linux-amd64
Linux ARM64 (Raspberry Pi, ARM servers)tpeek-linux-arm64
macOS Inteltpeek-macos-amd64
macOS Apple Silicontpeek-macos-arm64
Windows x64tpeek-windows-amd64.exe

Linux and macOS: download it straight into your PATH and make it executable.

$ sudo curl -L https://github.com/michelware/tpeek/releases/latest/download/tpeek-linux-amd64 -o /usr/local/bin/tpeek
$ sudo chmod +x /usr/local/bin/tpeek
$ tpeek -version        # prints the version

Windows: rename the file to tpeek.exe, place it in a folder listed in your PATH, and run it from a terminal (Windows Terminal recommended for colors).

From source, with Go 1.23 or newer:

$ git clone https://github.com/michelware/tpeek
$ cd tpeek
$ go build -o tpeek
$ ./build.sh            # or build every platform at once, into build/

2. Quick start

Your MySQL listens on 3306. Start TPeek on 8000 and forward to it:

$ tpeek -l 127.0.0.1:8000 -t 127.0.0.1:3306 -hex

Then point your application at 127.0.0.1:8000 instead of 127.0.0.1:3306. Nothing else changes for the app or the server: every byte is forwarded as is, and you see all of it. Stop with Ctrl+C.

See Data blocks and Connection events to read the output.

3. Command line flags

FlagDefaultMeaning
-lrequiredAddress and port TPeek listens on. Example: 127.0.0.1:8000.
-trequiredTarget address and port, where every connection is forwarded. Example: 127.0.0.1:3306.
-hexfalseShow data as a hexadecimal dump instead of plain text.
-nocolorfalseDisable colors.
-versionPrint the version and exit.

Colors are also turned off automatically when the output is not a terminal (file, pipe) or when the NO_COLOR environment variable is set.

Listening on 0.0.0.0 exposes the target to your whole network. tpeek -l 0.0.0.0:8000 -t 127.0.0.1:6379 makes a Redis that was only reachable from the machine itself reachable by anyone who can reach port 8000. Use 127.0.0.1 unless the client really runs on another machine.

4. Data blocks

One block is one Read() on the socket, exactly as your application would receive it.

┌── #1 🔵 CLIENT >> ── 14:32:01.479602 ── +682µs ── 70 bytes @ 0
     │   │              │                  │         │         │
     │   │              │                  │         │         └ offset of the first byte in this
     │   │              │                  │         │           direction's stream (0 = very first byte)
     │   │              │                  │         └ size of this read
     │   │              │                  └ time since the connection was accepted
     │   │              └ wall clock, microseconds
     │   └ direction: 🔵 CLIENT >> (client → server) or 🟢 SERVER << (server → client)
     └ connection number

Timing

+682µs and +4.195ms are measured from the moment the connection was accepted. The gap between a request and its answer is the difference between the two: here about 3.5 ms of server time.

Offset

Binary protocols often announce a length (“the next 89 bytes are one packet”). The offset tells you where each message starts and ends, even when it is split across several reads:

┌── #4 🟢 SERVER << ── ... ── 16384 bytes @ 0
┌── #4 🟢 SERVER << ── ... ── 16384 bytes @ 16384
┌── #4 🟢 SERVER << ── ... ── 2741 bytes @ 32768     ← 35509 bytes in total

5. Connection events

Events are printed on the same timeline as the data blocks, with the same microsecond clock.

EventMeaning
✅ #1 New connection from 127.0.0.1:52144A client connected to TPeek.
🔗 #1 client → [127.0.0.1:52145] → targetTPeek reached the target. The port in brackets is the one the target sees: use it to find this connection in the target's logs (e.g. MySQL SHOW PROCESSLIST).
❌ #1 Target connection failedThe target is down or unreachable (10 s timeout). The client is disconnected.
📭 #1 🔵 CLIENT >> finished sending (EOF)That side closed cleanly. The other direction keeps running until it is done too: half-close is passed through.
💥 #1 🔵 CLIENT >> read error: connection reset by peerThat side ended abruptly: crash, kill, network failure.
⚠️ #1 ... write failedData couldn't be delivered: the receiving side is gone.
🔌 #1 Connection closed after 1.523sSummary of the connection, with the bytes sent by each side.
Who stops first is often the answer to a bug. 📭 #1 🟢 SERVER << finished sending (EOF) after 30.002s means the server closed the connection by itself, probably an idle timeout.

6. Plain text mode

The default. Made for text protocols: HTTP, SMTP, Redis, IRC, JSON lines. The rules, byte by byte:

  1. Printable ASCII is shown as is.
  2. \n is a line break, \r\n is a single line break.
  3. Every other byte is shown as one . An é (2 bytes in UTF-8) shows as .., so the display always matches the byte count.

Control characters, including terminal escape codes, are never sent to your terminal: a server can't mess up or hijack your shell.

7. Hex mode

$ tpeek -l 127.0.0.1:8000 -t 127.0.0.1:6379 -hex

Works for any protocol: it shows the raw bytes, whatever they mean. Use it for binary protocols (MySQL, PostgreSQL, MQTT, gRPC, homemade formats) or when the exact bytes matter: CRLF vs LF, length prefixes, flags. Example with Redis, where $4 means “the next 4 bytes are the value”:

┌── #1 🔵 CLIENT >> ── 18:07:32.861274 ── +92.91ms ── 14 bytes @ 0
│ 00000000  2a 31 0d 0a 24 34 0d 0a  50 49 4e 47 0d 0a        |*1..$4..PING..|
└────────────────────────────────────────

┌── #1 🟢 SERVER << ── 18:07:32.861274 ── +92.91ms ── 7 bytes @ 0
│ 00000000  2b 50 4f 4e 47 0d 0a                              |+PONG..|
└────────────────────────────────────────

8. Recipes

# Database (MySQL, PostgreSQL...): binary protocol → hex
$ tpeek -l 127.0.0.1:8000 -t 127.0.0.1:3306 -hex

# Redis: text protocol → plain text is usually enough
$ tpeek -l 127.0.0.1:8000 -t 127.0.0.1:6379

# Plain HTTP API (no TLS)
$ tpeek -l 127.0.0.1:8080 -t api.internal:80

# Save a full trace (events + data, one timeline) to a file
$ tpeek -l 127.0.0.1:8000 -t 127.0.0.1:3306 > trace.log

# Only keep what matters
$ tpeek -l 127.0.0.1:8000 -t 127.0.0.1:3306 | grep -E "#3|💥"

To watch two services, run two TPeek instances on two ports.

9. Limitations

  • No TLS decryption. With HTTPS or MySQL over SSL, TPeek shows encrypted bytes. Put it on the unencrypted side (e.g. between a TLS-terminating proxy and the app), disable TLS in a test environment, or use mitmproxy / Fiddler for HTTPS.
  • The client must point to TPeek. If you can't change where the client connects, use a passive capture (Wireshark, tcpdump).
  • One target per instance.
  • The target sees TPeek's address, not the client's. IP allow-lists or MySQL accounts tied to a host ('user'@'10.0.0.5') see the proxy's address instead. The 🔗 line gives the mapping.
  • The terminal sets the pace. Data is forwarded before being printed, so a message is never delayed by the display, but a very slow terminal (huge hex dumps over SSH) can reduce throughput. Redirect to a file in that case.
  • Colors on Windows. The legacy console (conhost) doesn't render colors: use Windows Terminal or -nocolor. In Git Bash (mintty), the output isn't seen as a terminal, so colors are off.
  • Clock precision on Windows. Timestamps are in microseconds, but the Windows clock ticks in steps: several close events can show the same time. On Linux and macOS the precision is real.
